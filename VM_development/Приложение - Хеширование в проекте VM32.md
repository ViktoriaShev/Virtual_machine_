
## 1. Общее назначение подсистемы хеширования

Подсистема хеширования в VM32 является **базовым инфраструктурным компонентом**, а не вспомогательной утилитой. Она используется сразу в нескольких критически важных частях виртуальной машины: от хранения метаданных и кеширования до контроля целостности и диагностики исполнения.

На уровне архитектуры подсистема решает сразу несколько задач:

- обеспечивает **быстрый доступ** к часто используемым данным (метки, точки останова, символы);
    
- снижает вычислительные затраты за счёт **кеширования дорогих операций** (декодирование инструкций, потенциальная мемоизация);
    
- служит фундаментом для **контроля целостности и детерминированности** (CRC32, проверка состояния);
    
- задаёт **чёткую модель владения памятью**, что критично для стабильности долгоживущей VM.
    

Подсистема предоставляет:

- реализацию открытой хеш-таблицы с линейным пробированием и размером бакетов, кратным степени двойки;
    
- набор готовых `key_type_t` и `value_type_t` для типовых случаев (`uint32_t`, строки, указатели);
    
- реализацию CRC32 и вспомогательные функции для проверки состояния памяти и регистров;
    
- инфраструктуру для хранения внутренних таблиц VM (`labels`, `breakpoints`, `decoded_cache` и др.);
    
- единый и формализованный контракт владения данными через `.cpy` / `.del`.
    

Таким образом, хеширование в VM32 — это **общий механизм организации внутреннего состояния**, а не просто контейнер данных.

## 2. Что уже реализовано

### 2.1. Ядро хеш-таблицы

В основе подсистемы лежит собственная реализация хеш-таблицы с открытой адресацией:

- поддерживаются операции создания, удаления, вставки, поиска и проверки наличия ключа;
    
- используется линейное пробирование, что даёт хорошую кэш-локальность и предсказуемое поведение;
    
- размер таблицы всегда является степенью двойки, что позволяет заменить операцию `%` на дешёвый `& (m - 1)`;
    
- реализовано автоматическое перераспределение таблицы при превышении или падении коэффициента загрузки.
    

Выбор линейного пробирования и power-of-two размера — осознанный компромисс: он минимизирует накладные расходы, упрощает код и хорошо подходит для относительно небольших, но «горячих» таблиц VM.

---

### 2.2. Типы ключей и значений

Ключевая особенность архитектуры — **параметризация таблицы типами ключей и значений**.  
Каждый `key_type_t` / `value_type_t` определяет:

- как вычисляется хеш;
    
- как сравниваются элементы;
    
- как создаётся копия (ownership);
    
- как освобождается память.
    

Реализованы следующие стандартные типы:

- `uint32_key_type` / `uint32_value_type` — безопасное хранение числовых значений;
    
- `string_key_type` / `string_value_type` — строки с глубоким копированием через `strdup`;
    
- `ptr_key_type` / `ptr_value_type` — **без владения**, где таблица выступает лишь как индекс.
    

Последний вариант особенно важен: он позволяет использовать хеш-таблицу как кеш или индекс, не вмешиваясь в жизненный цикл объектов. Это критично для таких структур, как кеш декодированных инструкций.

> Архитектурный принцип: **таблица всегда делает ровно то, что описано в её типах**, и никогда не пытается «угадать», как управлять памятью.

---

### 2.3. CRC32 и контроль целостности

Подсистема хеширования также включает реализацию CRC32, используемую для:

- проверки детерминированности выполнения между циклами ПЛК;
    
- контроля целостности памяти и регистров;
    
- выявления скрытых недетерминированных эффектов.
    

CRC32 реализован с ленивой инициализацией таблицы, что снижает стартовые накладные расходы. Наличие как низкоуровневого API (`crc32_update`), так и высокоуровневых функций (`calculate_registers_hash`) делает подсистему удобной для повторного использования.

Важно, что CRC32 в VM32 — это **не криптографическая защита**, а инструмент диагностики и инженерного контроля.

---

### 2.4. Интеграция в VM32

Подсистема хеширования активно используется в `vm32.c`:

- `labels` — отображение имён в адреса;
    
- `breakpoints` — быстрый lookup точек останова;
    
- `decoded_cache` — кеш декодированных инструкций;
    
- `program_hash` — CRC32 загруженного бинарного образа.
    

Все таблицы создаются централизованно в `vm_tables_init()` и уничтожаются в `vm_tables_destroy()`. Это формирует чёткую точку жизненного цикла и упрощает управление ресурсами.

---

### 2.5. Кеш декодированных инструкций

Кеш декодированных инструкций — один из самых производительно значимых элементов VM32. Он позволяет:

- избежать повторного декодирования одной и той же инструкции;
    
- снизить нагрузку на CPU в циклическом режиме ПЛК;
    
- упростить последующую оптимизацию (профилирование, JIT).
    

При этом кеш накладывает строгие требования к **корректному управлению памятью** и **инвалидации при изменении кода**, что напрямую влияет на архитектуру value_type.

---

## 3. Ownership и интерфейсные инварианты

Подсистема хеширования в VM32 строится вокруг строгих инвариантов владения:

1. Таблица **всегда** работает с копиями ключей и значений, возвращёнными `.cpy`.
    
2. Таблица **всегда** освобождает эти копии через `.del`.
    
3. Таблица **никогда** не освобождает память, которой она не владеет.
    
4. Семантика владения полностью определяется типами, а не контекстом использования.
    

Это позволяет:

- локализовать ответственность за память;
    
- безопасно использовать таблицы в разных частях VM;
    
- избегать скрытых утечек и double-free.
    

Использование `ptr_value_type` — осознанный инструмент, а не лазейка. Он должен применяться только там, где жизненный цикл объекта управляется извне.

## 4. Корректное использование в VM

### 4.1. Инициализация / уничтожение

```
c
void vm_tables_init(void) {
    labels = hash_table_create(&string_key_type, &uint32_value_type);
    breakpoints = hash_table_create(&uint32_key_type, &uint32_value_type);
    decoded_cache = hash_table_create(&uint32_key_type, &ptr_value_type); // or custom decoded_value_type
}

void vm_tables_destroy(void) {
    if (labels) hash_table_destroy(labels);
    if (breakpoints) hash_table_destroy(breakpoints);
    if (decoded_cache) hash_table_destroy(decoded_cache);
}
```

### 4.2. Добавление меток (labels)

```
c
void labels_add(const char *name, uint32_t addr) {
    /* key copied with strdup, value copied as uint32 */
    hash_table_insert(labels, name, &addr);
}
```

### 4.3. Breakpoints

```
c
void bp_set(uint32_t addr) {
    uint32_t v = 1;
    hash_table_insert(breakpoints, &addr, &v);
}
bool bp_is_set(uint32_t addr) {
    return hash_table_contains(breakpoints, &addr);
}
```

### 4.4. Декодированный кеш (вариант с автоматическим free)

- Опция A: использовать `ptr_value_type` и обеспечивать самодельное free при перезаписи/при destroy — **не рекомендуется**, проще экспортировать value_type, который делает free. 
- Рекомендованный вариант: **создать** `decoded_instr_value_type` в `hashing.c` и экспортировать:

```
c
/* hashing.c */
static void *decoded_copy(const void *p) { return (void *)p; } // no deep copy
static void decoded_free(void *p) { free((void*)p); }

const value_type_t decoded_instr_value_type = {
    .cpy = decoded_copy,
    .del = decoded_free
};
/* в hashing.h: extern const value_type_t decoded_instr_value_type; */
```

и в `vm32.c`:

```
c
decoded_cache = hash_table_create(&uint32_key_type, &decoded_instr_value_type);
```

---

Здесь важно подчеркнуть общий принцип:  
**вся работа с таблицами должна происходить только после их инициализации и до уничтожения VM**.  
Любые попытки «ленивого» создания или частичного уничтожения таблиц усложняют reasoning и повышают риск ошибок.

---

## 5. Типовые ошибки и архитектурные ловушки

Этот раздел особенно важен, потому что большинство ошибок с хеш-таблицами — не синтаксические, а **семантические**.

- `static`-символы в `hashing.c` — это не просто ошибка линковки, а нарушение архитектурной границы.
    
- Передача адресов временных объектов опасна **только если** `.cpy` не делает копию — именно поэтому инварианты так важны.
    
- Кеш инструкций **обязан** инвалидироваться при изменении памяти — иначе VM теряет детерминированность.
    
- Потокобезопасность сознательно отсутствует, чтобы не вводить ложное ощущение безопасности.

## 6. Рекомендации по развитию

### Критически важно

Инвалидация кеша инструкций — это не оптимизация, а **требование корректности**.  
Без неё любое self-modifying поведение или повторная загрузка программы делает VM логически некорректной.

Экспорт `decoded_instr_value_type` — это устранение архитектурного несоответствия между таблицей и её содержимым.

---

### Полезные расширения

Symbol table, profiler и opcode stats не меняют семантику VM, но радикально повышают наблюдаемость и отладочность системы. Это особенно важно для ВКР и промышленной демонстрации.

---

### Долгосрочные идеи

String pool, snapshots и JIT логично вписываются в текущую архитектуру именно потому, что база хеширования уже формализована.

# 7. API / reference (коротко)

### hash_table API

- `hash_table_t *hash_table_create(const key_type_t *k, const value_type_t *v);`
    
- `void hash_table_destroy(hash_table_t *table);`
    
- `void hash_table_insert(hash_table_t *table, const void *key, const void *value);`
    
- `void *hash_table_lookup(hash_table_t *table, const void *key);` — возвращает `val` (тип `void*`) или `NULL`.
    
- `void hash_table_delete(hash_table_t *table, const void *key);`
    
- `bool hash_table_contains(hash_table_t *table, const void *key);`
    

### key_type_t / value_type_t

```c
typedef struct {
    uint32_t (*hash)(const void *key);
    bool (*cmp)(const void *a, const void *b);
    void *(*cpy)(const void *key);  // create owned copy
    void (*del)(void *key);         // free owned copy
} key_type_t;
```

Value type is same shape.

**Rule:** `cpy` must allocate or return pointer which table will own and later pass to `del`.

# 8. Тесты и бенчмарки (как проверить)

### Модульные тесты (рекомендуемые)

- **hash_table_basic** — проверка операций `insert`, `lookup`, `delete`, `contains` для ключей и значений типов `uint32` и `string`.
    
- **resize** — вставка количества элементов, превышающего `LOAD_FACTOR_MAX × size`; проверка того, что размер таблицы увеличился вдвое и все элементы по-прежнему корректно находятся.
    
- **decoded_cache_lifecycle** — вставка декодированных инструкций в кеш, вызов `hash_table_destroy` и проверка отсутствия утечек памяти (корректная работа `val_del`).
    
- **invalidation** — вызов `load_program`, затем `decoded_cache_invalidate_range`; проверка, что поиск по соответствующему адресу возвращает `NULL` после инвалидирования кеша.
    

### Микробенчмарки

- Измерение среднего времени декодирования инструкций **с кешем и без кеша**:
    
    - подготовить программу с повторяющимися последовательностями инструкций;
        
    - выполнить `N` итераций, измеряя **только** время операций декодирования;
        
    - ожидаемый прирост производительности — **20–30 %**, в зависимости от набора инструкций.
        

### Инструменты

- Компиляция с флагами  
    `-O2 -fsanitize=address,undefined`  
    на этапе разработки для выявления ошибок работы с памятью и неопределённого поведения.
    
- Использование  
    `valgrind --leak-check=full`  
    или AddressSanitizer (ASAN) для поиска утечек памяти.

# 9. Примеры полезных вспомогательных функций (код)

### decoded_cache_clear / invalidate_range

```c
/* clear whole cache */
void decoded_cache_clear(void) {
    if (!decoded_cache) return;
    /* teardown and recreate for simplicity */
    hash_table_destroy(decoded_cache);
    decoded_cache = hash_table_create(&uint32_key_type, &decoded_instr_value_type);
}

/* invalidate range (inclusive start, size bytes) */
void decoded_cache_invalidate_range(uint32_t start, uint32_t size) {
    if (!decoded_cache) return;
    uint32_t end = start + size;
    for (uint32_t addr = start; addr < end; addr += 4) {
        hash_table_delete(decoded_cache, &addr);
    }
}
```

**Где вызывать**:

- `load_program()` — после загрузки: `decoded_cache_clear()`
    
- при записи в mem: `decoded_cache_invalidate_range(write_addr, write_len)`

# 10. Безопасность, производительность и ограничение

- **Производительность**: линейное пробирование даёт отличную кэш-локальность, но при высокой заполненности ( >50%) увеличиваются цепочки — resize предусмотрён.
    
- **Hash function**: сейчас CRC32 для ключей — хорош для uniform распределения, но более быстрый хеш (FNV1a) можно выбрать, если вычисление CRC32 на ключах становится узким местом. У вас флаг `vm_config.hash_algo` — можно переключать.
    
- **Memory use**: таблицы занимаются malloc/free при вставках — для очень горячих путей (миллионы вставок) подумать про пул аллокаций.
    
- **Thread-safety**: отсутствует — если будет многопоточность, добавьте мьютексы.
