

Данная виртуальная машина предназначена для запуска программ, предварительно преобразованных в бинарный формат. Процесс работы с проектом состоит из нескольких последовательных этапов: сборки исполняемых файлов, преобразования исходных программ из ассемблерного представления в бинарное, запуска виртуальной машины и, при необходимости, выполнения тестов. Ниже описан порядок действий как для обычного пользователя, так и для разработчика, который работает с исходным кодом проекта.

## Подготовка окружения

Перед началом работы необходимо убедиться, что в системе установлены средства сборки. Для запуска проекта на локальной машине требуется `gcc` и `make`. Если планируется кросс-компиляция, дополнительно должны быть доступны `aarch64-linux-gnu-gcc` для платформы `arm64` и `arm-linux-gnueabihf-gcc` для платформы `arm32`. Вспомогательные утилиты `lcov` и `genhtml` используются только при генерации отчёта о покрытии тестами.

## Сборка проекта

Для полной сборки проекта достаточно выполнить команду:

```bash
make
```

В ходе выполнения этой команды Makefile автоматически создаёт необходимые каталоги для артефактов сборки, после чего компилирует два основных компонента проекта: конвертер и саму виртуальную машину. Конвертер собирается как отдельная служебная программа и используется для преобразования файлов с расширением `.asm` в бинарные файлы `.bin`. Виртуальная машина собирается в исполняемый файл, имя которого зависит от выбранной целевой платформы.

По умолчанию сборка выполняется для хостовой системы, то есть для той машины, на которой производится запуск команды. Если требуется собрать проект под другую архитектуру, необходимо явно указать параметр `TARGET`. Например:

```bash
make TARGET=host
make TARGET=arm64
make TARGET=arm32
```

При значении `host` используется обычный компилятор `gcc`, при `arm64` — кросс-компилятор `aarch64-linux-gnu-gcc`, а при `arm32` — `arm-linux-gnueabihf-gcc`. Таким образом, один и тот же исходный код может быть подготовлен для разных платформ без изменения структуры проекта.

## Преобразование программ в бинарный формат

Исходные программы виртуальной машины хранятся в каталоге `asm/` в текстовом формате. Для того чтобы виртуальная машина могла их загрузить и исполнить, они должны быть преобразованы в бинарное представление. Эта операция выполняется автоматически при запуске целевой команды `run`, однако её можно выполнить и отдельно:

```bash
make convert
```

В результате все файлы вида `asm/*.asm` будут преобразованы в бинарные файлы и помещены в каталог `build/bin/`. Именно этот каталог затем используется как источник программ для виртуальной машины.

Таким образом, типичный порядок работы выглядит следующим образом: программист размещает или редактирует `.asm`-файлы в `asm/`, затем запускает `make convert`, после чего в `build/bin/` появляются готовые `.bin`-файлы. Эти бинарные файлы уже являются входными данными для исполнения.
## Запуск виртуальной машины

Для запуска виртуальной машины на хостовой системе используется команда:

```bash
make run
```

Если необходимо, можно указать дополнительные аргументы через переменную `ARGS`:

```bash
make run ARGS="--verbose"
```

При запуске выполняется следующий порядок действий. Сначала проект собирается, если это ещё не было сделано. Затем конвертер создаёт бинарные файлы программ из каталога `asm/`. После этого виртуальная машина запускается и получает в качестве входных данных каталог `build/bin`, в котором находятся подготовленные программы. Иначе говоря, виртуальная машина не работает напрямую с исходными `.asm`-файлами, а загружает уже готовые бинарные данные.

Если проект собирается под архитектуру, отличную от хостовой, команда `make run` не запускает программу на текущем компьютере, а только сообщает, что скомпилированный бинарный файл необходимо перенести на целевое устройство. Это связано с тем, что исполняемый файл в таком случае предназначен для другой архитектуры.

Запуск возможен и вручную, без Makefile, если требуется прямой контроль над параметрами. В этом случае исполняемому файлу нужно передать путь к каталогу, содержащему бинарные программы. Общий формат запуска выглядит так:
```
./build/vm32_host <program_dir> [options]
```

Здесь `<program_dir>` — это каталог с бинарными файлами, а `options` — дополнительные параметры конфигурации виртуальной машины.
## Параметры запуска и настройка поведения VM

В текущей реализации настройки передаются не через отдельный конфигурационный файл, а через командную строку. Это означает, что поведение виртуальной машины задаётся непосредственно при запуске, без необходимости редактировать отдельные поднастройки вручную.

Первым обязательным параметром является путь к каталогу программ. Если он не указан явно, виртуальная машина использует значение по умолчанию `build/programs`. Однако при обычном запуске через Makefile используется `build/bin`, поэтому для стандартного сценария лучше ориентироваться именно на него. Это означает, что при ручном запуске следует явно передавать актуальный каталог с бинарными файлами, например:
```
./build/vm32_host build/bin
```
После пути к каталогу можно указать дополнительные параметры конфигурации. Параметр `--clock-rate-hz N` задаёт частоту тактирования в герцах и определяет, как виртуальная машина интерпретирует временные интервалы. Параметр `--cycle-time-ms N` задаёт длительность одного цикла в миллисекундах. Оба значения должны быть больше нуля, иначе запуск будет отклонён как некорректный.

Флаг `--enable-cycle-check` включает контроль превышения допустимого времени цикла, а `--disable-cycle-check` отключает этот контроль. Аналогично, `--enable-hash-check` и `--disable-hash-check` управляют проверкой хэша, а `--enable-tick-timing` и `--disable-tick-timing` отвечают за измерение времени тиков. Эти параметры позволяют адаптировать поведение виртуальной машины под режим отладки, тестирования или производственного запуска.

Да, вот пример **полного запуска с настройкой всех полей `vm_config_t`** через командную строку.

### Прямой запуск бинарника

```bash
./build/vm32_host build/bin \
  --clock-rate-hz 1000000 \
  --cycle-time-ms 10 \
  --enable-cycle-check \
  --enable-hash-check \
  --enable-tick-timing \
  --hash-algo crc32
```

Здесь:

- `build/bin` — каталог с бинарными программами `*.bin`;
    
- `--clock-rate-hz 1000000` задаёт частоту в 1 000 000 Гц;
    
- `--cycle-time-ms 10` задаёт длительность цикла в 10 мс;
    
- `--enable-cycle-check` включает проверку превышения времени цикла;
    
- `--enable-hash-check` включает проверку хэша;
    
- `--enable-tick-timing` включает измерение времени тиков;
    
- `--hash-algo crc32` выбирает алгоритм хэширования.
    

### То же самое через `make run`

```bash
make run ARGS="--clock-rate-hz 1000000 --cycle-time-ms 10 --enable-cycle-check --enable-hash-check --enable-tick-timing --hash-algo crc32"
```

В этом варианте `make` сам передаст в VM каталог `build/bin`, а всё, что указано в `ARGS`, добавится после него.

### Если нужно отключить проверки

У пары флагов есть альтернативы, например:

```bash
./build/vm32_host build/bin \
  --clock-rate-hz 1000000 \
  --cycle-time-ms 10 \
  --disable-cycle-check \
  --disable-hash-check \
  --disable-tick-timing \
  --hash-algo fnv1a
```

Важно, что для одного запуска используется только один вариант из каждой пары: либо `--enable-*`, либо `--disable-*`.

Если нужно, я могу сразу оформить это как готовый подпункт для твоего руководства в академическом стиле.
Дополнительно можно выбрать алгоритм вычисления хэша с помощью параметра `--hash-algo`. Поддерживаются значения `crc32` и `fnv1a`:
```
./build/vm32_host build/bin --hash-algo crc32
```
или
```
./build/vm32_host build/bin --hash-algo fnv1a
```
Если передать некорректное значение, виртуальная машина выдаст сообщение об ошибке и завершит работу. Для быстрого просмотра всех допустимых параметров можно использовать:
```
./build/vm32_host --help
```
или аналогично через Makefile, если он передаёт аргументы напрямую.
## Запуск в режиме разработки

Для разработчика особенно полезен режим отладки, так как он отключает оптимизации и включает отладочную информацию. Это позволяет удобнее анализировать поведение программы, использовать отладчик и точнее отслеживать ошибки. Для этого следует выполнить:

```bash
make debug
```

В этом режиме проект пересобирается с нуля с параметрами `-O0` и `-g`. Такой вариант сборки не предназначен для производительного запуска, но является предпочтительным при поиске ошибок, анализе логики исполнения и проверке внутренних состояний виртуальной машины.

## Запуск тестов

Для проверки корректности реализации предусмотрен автоматический запуск тестов. Чтобы собрать и выполнить все тестовые программы, достаточно использовать команду:

```bash
make test
```

Makefile найдёт все исходные файлы в каталоге `tests/`, скомпилирует их вместе с ядром виртуальной машины и затем последовательно запустит каждый тестовый исполняемый файл. Такой подход позволяет проверять отдельные части системы независимо от основного сценария запуска.

Дополнительно предусмотрен специальный тест для проверки механизма hot reload:

```bash
make hot_reload_test
```

После сборки соответствующий исполняемый файл располагается в каталоге `build/bin/`. Этот тест полезен при работе с динамической перезагрузкой программ и изменениями файлов в процессе выполнения.

## Генерация отчёта о покрытии

Если требуется оценить полноту тестирования, можно собрать проект с поддержкой покрытия и затем сформировать HTML-отчёт. Для этого используются команды:

```bash
make coverage
make coverage-report
```

Первая команда пересобирает проект с флагами, необходимыми для сбора информации о покрытии, и запускает тесты. Вторая команда формирует итоговый отчёт в каталоге `build/coverage/`. Этот отчёт позволяет разработчику увидеть, какие участки кода были выполнены во время тестирования, а какие остаются непокрытыми.

## Очистка артефактов сборки

После экспериментов, отладки или повторной сборки может потребоваться удалить все созданные файлы. Для этого используется команда:

```bash
make clean
```

Она полностью удаляет каталог `build/`, включая скомпилированные объекты, бинарные файлы и промежуточные результаты.

## Назначение проекта с точки зрения разработчика

С точки зрения программиста, данный проект организован как набор логически разделённых компонентов. Исходный код виртуальной машины находится в каталоге `src/`, заголовочные файлы — в `include/`, служебные инструменты — в `tools/`, тесты — в `tests/`, а исходные программы на ассемблере — в `asm/`. Такой подход позволяет отделить ядро виртуальной машины от вспомогательных утилит и сценариев проверки.

Особое внимание в Makefile уделено тому, что ядро виртуальной машины может собираться как отдельно от точки входа `main`, так и вместе с ней. Это достигается через использование макроса `VM_NO_MAIN` при компиляции объектных файлов ядра. Благодаря этому один и тот же код может использоваться и для основного исполняемого файла, и для тестов, что снижает дублирование и упрощает сопровождение проекта.

Кроме того, схема сборки предусматривает кросс-компиляцию. Это означает, что программист может собирать виртуальную машину не только для текущей системы, но и для целевых архитектур ARM, сохраняя единый процесс сборки. Для практической работы это особенно важно, если проект предполагает запуск на встраиваемых устройствах или в изолированной среде с другой архитектурой процессора.

## Типовой порядок работы

На практике обычный пользователь или разработчик обычно выполняет следующий сценарий: сначала очищает старые артефакты, затем собирает проект, после чего запускает виртуальную машину или тесты. Для повседневной работы достаточно команды `make run`, а для проверки изменений в коде целесообразно использовать `make test` или `make debug`. Если изменяются исходные программы в каталоге `asm/`, необходимо повторно выполнить преобразование в бинарный формат, чтобы новые версии программ были подхвачены виртуальной машиной.
