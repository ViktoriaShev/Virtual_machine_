

# 1) Общая стратегия (слои тестирования)

1. **Smoke / Sanity (быстрые)** — запускают пару очень коротких программ и проверяют, что VM стартует, выполняет инструкции и корректно выходит. Должен занимать << 1s.
    
2. **Functional / Acceptance (черный ящик)** — прогон реальных .bin (assembler -> bin) и проверка семантики: арифметика, ветвления, стеки, чтение/запись памяти. Включай режимы tick_timing = true/false.
    
3. **Timers / PLC semantics (корректность IEC)** — отдельные тесты TON/TOF/TP в разных режимах (cycle-based и tick-based).
    
4. **Edge cases / Error handling** — неверные opcodes, выход за границы памяти, деление на 0, декод-кэш, повторные HALT/EXIT.
    
5. **Regression / Fuzz** — генерация случайных/мутационных бинарников, проверка на падения/UB.
    
6. **Performance / Timing** — проверка, что цикл не выходит за cycle_time_ms, измерение throughput, проверка предупреждений overrun.
    
7. **Sanitizers & Static Analysis** — запуск под ASAN/UBSAN/LSAN, статический анализ (clang-tidy).
    

---

# 2) Приоритет — что сделать сначала

1. **Smoke**: `nop`, `add`, `halt` — проверить корректный вывод логов.
    
2. **Opcode correctness**: набор коротких программ для каждой группы опкодов (arith, logic, cmp, mem, jmp).
    
3. **Decoder/cache**: тест с instruction alignment и кешом (одно и то же место несколько раз).
    
4. **Timers basic**: 2–3 теста для TON/TOF/TP в cycle-based (vm_config.enable_tick_timing=false) — самый важный уровень.
    
5. **Tick mode**: те же таймеры с enable_tick_timing=true (real time).
    
6. **Sanitizers**: собрать и прогнать тесты под ASAN.

# 3) Конкретные функциональные тесты (с ожидаемым поведением)

### A. Smoke: add+halt

asm (псевдо):

```
; program: smoke.asm
ADD R2, R0, #5   ; R2 <- 5
HALT
```

Ожидаем: при старте в логах видно изменение R2 → 5, модуль завершён.

### B. Decoder / PC increment

- Программа с последовательностью инструкций, проверка, что PC увеличивается на 4 если инструкция не меняет PC.
    
- Тест на недопустимый opcode — VM должна корректно логировать ошибку и остановиться.
    

### C. TON (cycle-based) — краткий дизайн теста

Параметры:

- `vm_config.cycle_time_ms = 1000` (1 цикл = 1000 ms)
    
- В программе: устанавливаем R10 = timer id (например 0), R11 = input (1). Инструкция `TON R10, R11, #3000` (PT = 3000 ms).  
    Тестовый сценарий:
    
- Запусти VM на 4 цикла (каждый цикл — прогони модули). В начале цикла 1..4 опрашиваем reg[10] после `op_ton` — ожидаем: `0,0,0,1` (Q=1 только после третьего полного цикла, т.е. при time_ms >= start + 3000).  
    (Причина: мы обновляем time_ms один раз в конце цикла; таймер должен учитывать именно это.)
    

### D. TOF (cycle-based)

- Set input high for some cycles, then drop to 0. PT = 2000 ms → Q should remain 1 for next two cycles, then become 0.
    

### E. TP (pulse)

- Rising edge should produce a single-cycle Q=1, then 0 after PT if PT shorter/longer — в соответствии с PT.

# 4) Как автоматизировать: blackbox harness (bash + python)

1. **asm → bin**: ты уже имеешь assembler (asm2bin). Используем его для сборки тестов.
    
2. **Запуск VM**: запускаем твою `vm` с нужными программами и перехватываем stdout.
    
3. **Парсинг логов**: в логах у тебя есть подробная печать изменений регистров — парсер вытащит нужные значения.
    
4. **Ассерты**: Python проверит ожидания по каждому циклу.
    

Ниже — примерный `run_test.sh` + Python parser `check_log.py`.

---

### run_test.sh

```bash
#!/usr/bin/env bash
set -euo pipefail

ASM2BIN=./asm2bin
VM=./vm32         # твой исполняемый
OUTDIR=tests/out
mkdir -p "$OUTDIR"

# example: build timer_test.asm -> timer_test.bin
$ASM2BIN tests/asm/timer_ton.asm "$OUTDIR/timer_ton.bin"

# run VM (capture stdout)
$VM "$OUTDIR/timer_ton.bin" > "$OUTDIR/timer_ton.log" 2>&1

# run checker
python3 tests/check_log.py "$OUTDIR/timer_ton.log" --test timer_ton
if [ $? -eq 0 ]; then
  echo "timer_ton: PASS"
else
  echo "timer_ton: FAIL"
  exit 2
fi
```

---

### tests/check_log.py (упрощённый)

```python
#!/usr/bin/env python3
import re
import sys
import argparse

# Примитивный парсер, ищем изменения регистров "R010: ... -> 0x00000001"
reg_change_re = re.compile(r"R(?P<idx>\d{3}): .*-> 0x(?P<after>[0-9A-Fa-f]{8})")

def extract_registers(log_text, reg_idx):
    # Вернёт последовательность значений, которые появлялись в логах (после изменений)
    vals = []
    for m in reg_change_re.finditer(log_text):
        idx = int(m.group("idx"))
        if idx == reg_idx:
            vals.append(int(m.group("after"), 16))
    return vals

def check_timer_ton(log_text):
    # ожидаем, что R010 изменялся к 1 только на 4-ой позиции по сценарию: 0,0,0,1
    vals = extract_registers(log_text, 10)  # R010
    # Небольшая гибкость: возьмём последние 4 изменения, сравним с эталоном
    if len(vals) < 4:
        print("Too few R010 changes:", vals)
        return False
    sample = vals[:4]
    print("R010 sample:", sample)
    return sample == [0,0,0,1]

if __name__ == "__main__":
    p = argparse.ArgumentParser()
    p.add_argument("logfile")
    p.add_argument("--test", choices=["timer_ton"], required=True)
    args = p.parse_args()

    txt = open(args.logfile,"r",encoding="utf-8").read()

    ok = False
    if args.test == "timer_ton":
        ok = check_timer_ton(txt)
    print("OK" if ok else "FAILED")
    sys.exit(0 if ok else 2)
```

_Примечание:_ твой реальный лог-формат может отличаться — подбери `reg_change_re` по точной печати. Если в логах нет удобной структуры, добавь опцию в VM, чтобы печатать короткие machine-readable строки (см. ниже).

# 5) Совет: сделать «machine-readable» output mode

Для автоматических тестов очень удобно иметь компактный формат (JSONL) с состоянием в конце каждого цикла, например:

```json
{"cycle":1,"time_ms":1000,"regs":[...],"changes":[{"reg":10,"before":0,"after":0},...]}
```

Добавь флаг `--json-cycles` или `--test-mode` — и тестовый harness будет просто читать JSON и делать жёсткие ассерты. Это гораздо надежнее, чем парсинг human logs.

Короткий пример C-функции (псевдо), которую можно вызывать в конце каждого цикла:

```c
void dump_cycle_state_json(FILE *f) {
    fprintf(f, "{\"cycle\":%u,\"time_ms\":%llu,\"regs\":[", cycle_count, (unsigned long long)time_ms);
    for (int i=0;i<REG_COUNT;i++) {
      fprintf(f, "%u", reg[i]);
      if (i+1<REG_COUNT) fputc(',',f);
    }
    fprintf(f, "]}\n");
}
```

# 6) Сборка для тестов: флаги компиляции

Собирай тестовую сборку с sanitizer’ами и дебагом:

```
CFLAGS="-g -O1 -fsanitize=address,undefined -fno-omit-frame-pointer"
make clean && make CFLAGS="$CFLAGS"
```

Запусти тесты, поймай UB/ASAN.

# 7) CI (мини-пример GitHub Actions)

Создай `.github/workflows/ci.yml`:

```yaml
name: CI
on: [push, pull_request]
jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Install deps
        run: sudo apt-get update && sudo apt-get install -y build-essential
      - name: Build
        run: make CFLAGS="-O1 -g -fsanitize=address,undefined"
      - name: Run smoke tests
        run: ./tests/run_all_smoke.sh
```

(Добавь шаги для lcov/coverage при желании.)
