По твоему дереву видно, что база уже неплохая: есть арифметика, ветвления, безопасность памяти, загрузчик, hot reload, регрессия по hash bounds, unit/stress для хэшей и unit для таймеров. Это уже не “пустой” проект.

Но для байткод-интерпретатора уровня production у тебя всё ещё есть несколько заметных дыр.

## Что сейчас закрыто

У тебя уже есть покрытие для:

- арифметики и деления на ноль;
    
- базового control flow;
    
- проверки некорректного opcode;
    
- защиты части memory boundary;
    
- загрузки нескольких модулей;
    
- hot reload по смене содержимого;
    
- hash-логики и регрессии по выходу за границы;
    
- базовых таймеров;
    
- стресс-теста hash table.
    

## Чего не хватает в тестах

### 1) Полного покрытия инструкций

Сейчас есть только часть ISA. Не вижу тестов на:

- `AND / OR / XOR / NOT`;
    
- сдвиги (`SHL / SHR / SAR`, если есть);
    
- сравнения (`CMP`, `SET*`);
    
- `LOAD / STORE` всех размеров;
    
- `PUSH / POP / CALL / RET`, если стек есть;
    
- `NOP`/`HALT` как отдельные semantics tests, а не просто как часть программы.
    

Нужно не просто “программа отработала”, а отдельные тесты на каждую инструкцию и каждый режим адресации.

### 2) Границы и ошибки памяти

Один тест на `vm_mw32/vm_mr32` и один на `DEMUX` — это мало. Не хватает:

- записи/чтения ровно на последнем валидном байте;
    
- crossing boundary на 1 байт;
    
- невыравненного доступа;
    
- отрицательных/битых адресов, если они возможны через декодирование;
    
- чтения из неинициализированной области;
    
- проверки, что память не портится при отказе операции.
    

### 3) Семантика ошибок, а не только “не упало”

Сейчас часть тестов проверяет, что VM остановилась, но не проверяет:

- какой именно код ошибки вернулся;
    
- изменился ли `PC`;
    
- был ли выставлен fault/state flag;
    
- остались ли регистры неизменными после фейла.
    

Особенно это важно для:

- `DIV by zero`;
    
- invalid opcode;
    
- out-of-bounds memory access;
    
- bad jump target.
    

### 4) VM lifecycle

Я не вижу отдельного блока тестов для жизненного цикла VM:

- `vm_create / vm_destroy`;
    
- `vm_init_defaults`;
    
- повторный `start/stop`;
    
- `stop_requested`;
    
- повторная инициализация;
    
- очистка после ошибки загрузки;
    
- корректность состояния после reset.
    

Это отдельный пласт, и он очень важен для интеграции с runtime.

### 5) Hot reload без happy path

Сейчас есть позитивный сценарий “файл поменялся → reload”. Не хватает:

- reload без изменений;
    
- reload с частично битым файлом;
    
- reload с несовместимой версией/сигнатурой;
    
- reload во время исполнения;
    
- rollback при ошибке загрузки;
    
- проверка, что старое состояние либо сохраняется, либо сбрасывается строго по контракту.
    

### 6) I/O и PLC-модули

Это самая большая архитектурная дыра, если у тебя интерпретатор реально должен жить рядом с PLC-портами.

Не хватает тестов на:

- маппинг входных/выходных каналов в память VM;
    
- устойчивость к изменению входа в середине цикла;
    
- latch/edge behavior;
    
- debounce, если он нужен;
    
- несколько модулей I/O одновременно;
    
- горячее подключение/отключение модуля;
    
- конфликт адресов между модулями.
    

То есть нужен отдельный слой abstraction + mock для I/O.

### 7) Таймеры только unit-уровня

Есть `timers_unit_test.c`, но нет интеграции с циклом VM:

- таймеры внутри run loop;
    
- зависимость от `cycle_time_ms`;
    
- сброс/пауза/возобновление;
    
- переполнение времени;
    
- несколько таймеров одновременно;
    
- детерминированность при одинаковом времени.
    

### 8) Negative tests для loader

Сейчас loader проверяется только на нормальную загрузку. Не хватает:

- пустой директории;
    
- файла не того формата;
    
- truncated binary;
    
- oversized program;
    
- дублирующихся модулей;
    
- неверного порядка модулей;
    
- битого заголовка/сигнатуры, если они есть.
    

### 9) Fuzz / property-based слой

Для интерпретатора это очень желательно:

- случайные байткоды;
    
- случайные последовательности инструкций;
    
- random reload/load cycles;
    
- long-run stress на тысячи/миллионы шагов;
    
- проверка, что VM не утекает и не падает.
    

Сейчас у тебя есть только `hash_table_stress_test`, а для VM такого класса тестов не видно.

## Какие модули, судя по тестам, ещё нужны

### 1) Validator байткода

Очень нужен отдельный модуль до запуска программы:

- проверка opcode;
    
- проверка jump targets;
    
- проверка таблиц;
    
- проверка адресов;
    
- проверка размеров модулей.
    

Без этого ошибки ловятся только в runtime.

### 2) I/O abstraction layer

Нужен слой между VM и железом:

- чтобы тестировать без реального PLC;
    
- чтобы подменять устройства mock-объектами;
    
- чтобы не было прямой зависимости VM от конкретного модуля.
    

### 3) Runtime boundary / scheduler control

Нужен явный контракт на:

- один шаг;
    
- один цикл;
    
- остановку;
    
- watchdog;
    
- предел выполнения за тик.
    

Судя по тестам, часть логики это уже предполагает, но отдельного покрытия нет.

### 4) Trace / debug snapshot

Для отладки полезно иметь:

- снимок регистров;
    
- снимок PC;
    
- историю выполненных инструкций;
    
- hash состояния на каждом шаге.
    

### 5) Unified error model

Сейчас тесты местами просто ждут `0` или `-1`. Для серьезной VM лучше иметь:

- нормальные error codes;
    
- различие между decode error, memory fault, reload fault, runtime fault;
    
- предсказуемое поведение после ошибки.

## Ещё один важный момент по текущим тестам

У тебя в `arithmetic_test.c` деление на ноль проверяется как “safe path = 0”. Это нормально только если это часть спецификации. Если по контракту VM должна выдавать fault или error code, то тест сейчас слишком мягкий: он проверяет результат, но не проверяет правильную реакцию системы.

И ещё: в `safety_memory_test.c` ты вызываешь `vm->op_ex[OP_DEMUX](...)` напрямую. Это полезно для unit-level проверки, но обязательно нужен ещё тест через полноценное выполнение инструкции, иначе можно пропустить баги в декодере и диспетчере.
