# Project system — Development Rules

## 1. Назначение документа

Данный документ описывает **обязательные правила разработки** проекта `system`.

Цель документа:
- зафиксировать единый стиль разработки,
- предотвратить архитектурную деградацию,
- обеспечить предсказуемость и сопровождаемость кода.

Все правила в этом документе считаются **обязательными**.

---

## 2. Общие требования

### 2.1 Язык и стандарт

- Язык разработки: **C++**
- Минимальный стандарт: **C++20**
- Использование нестандартных расширений запрещено
- Компиляция должна проходить без предупреждений

Флаги компиляции (обязательно):
- `-Wall`
- `-Wextra`
- `-Werror`

---

## 3. Архитектурные правила

### 3.1 Компоненты

- Любая логическая подсистема оформляется как компонент
- Все компоненты реализуют интерфейс `IComponent`
- Компоненты **не создают** другие компоненты
- Компоненты **не владеют** глобальными объектами

Запрещено:
- Singleton
- static state
- скрытые зависимости

---

### 3.2 Жизненный цикл

- Вся инициализация ресурсов — в `init()`
- Запуск логики — в `start()`
- Освобождение ресурсов — в `stop()`
- `stop()` обязан быть безопасным при частичной инициализации

---

### 3.3 SystemBus

- Все зависимости получаются через `SystemBus`
- Прямые зависимости между компонентами запрещены
- SystemBus не управляет временем, потоками и состоянием

---

## 4. System Layer

- System Layer изолирует платформу исполнения
- Core-уровень не знает о конкретной ОС
- Все системные функции предоставляются через интерфейсы

---

## 5. Логирование

- Использование `std::cout` и `std::cerr` в Core запрещено
- Логирование осуществляется только через `ILogger`
- System Layer реализует вывод логов

---

## 6. Event System

- События используются для слабосвязного взаимодействия
- Event delivery синхронная
- События не должны изменять глобальное состояние напрямую

---

## 7. Стиль кода

### 7.1 Именование

- Namespace: `system_runtime`
- Интерфейсы: `I<Name>`
- Компоненты: `<Name>Component`
- Файлы: `PascalCase.h / PascalCase.cpp`

---

### 7.2 Заголовочные файлы

- Каждый `.h` файл должен быть самодостаточным
- Использовать `#pragma once`
- Минимизировать includes

---

### 7.3 Память

- Предпочтительно `std::unique_ptr` / `std::shared_ptr`
- Запрещено ручное управление памятью (`new` / `delete`)
- Владение объектами должно быть очевидным

---

## 8. Ошибки и обработка

- Ошибки инициализации возвращаются через `bool`
- Исключения в Core не используются
- Поведение при ошибках должно быть предсказуемым

---

## 9. Git и workflow

### 9.1 Коммиты

- Один коммит — одна логическая задача
- Коммиты должны собираться
- Сообщения коммитов — осмысленные

---

### 9.2 Структура репозитория

- `build/` никогда не коммитится
- Документация хранится в `doc/`
- Временные файлы запрещены

---

## 10. Эволюция проекта

Любые изменения, затрагивающие:
- архитектуру,
- жизненный цикл,
- модель исполнения,

должны:
- быть задокументированы,
- обсуждены,
- зафиксированы в `doc/`.

---

## 11. Заключение

Соблюдение этих правил является обязательным условием:
- масштабируемости проекта,
- корректной работы runtime,
- долгосрочной поддержки.

Нарушение правил рассматривается как архитектурная ошибка.
